## 5. 规则与自动检查

内核检查内容结构、依赖和课程可达性；玩法包检查作品、参考解与 naive 解。教学质量由作者和评审判断。

| 提供者 | 检查 |
|---|---|
| 内核 | schema、引用、直接依赖、锁定、覆盖冲突、层权限、id 不变、包代码边界 |
| 内核 | `set`、`list` 不重复，`edges` 和标签嵌套无环，标签成员类型与消歧 |
| 内核 | 任务与关卡解锁可达，章的 `rows` 一行至多三个位置，后置关排在前置关之后 |
| 内核 | 同一课程内，另一条先修链已保证完成的直接先修连线会产生警告 |
| 包 | 参考解通过、naive 解失败、作品和玩法的一致性 |
| `circuit` | 端口与运算类型、设置、封装作品与托盘结构 |
| `progress` | 对象轨迹的目标、阶段和通过条件 |
| `progress` | 对象阶段、发放及依赖引用，按课程策略启用 |
| `circuit` | 课程启用的元件可用性、托盘引入来源与沿用依赖 |

**存在性检查只有一份。** `engine/existence.js` 按 schema 收集字段引用、覆盖目标、集合补丁的成员与边、标签、进度字段的元件引用及依赖选择，对照 manifest 的公开身份与代码登记表检查。目标须由所属命名空间声明或由代码登记。加载和引用展开只处理结构、集合与成环，存在性问题统一汇总。

问题保留 `rule`、`layer`、`kind`、`target`、`member?`、`reason`、`at`、`says`，另有 `object: { kind, name, member?, override? }` 与 `path`。存在性问题的 `rule` 为 `exists`，`reason` 为 `missing`、`ambiguous` 或 `undeclared dependency`。`name` 是对象全名，标签带成员类型；覆盖位置设 `override: true`，覆盖目标本身的 `path` 为空串。字段路径如 `tasks[0].solution`；配置位置如 `{ kind: "package", name: "example" }` 与 `uses[0]`。同一原始字段只报告一次，不同对象、成员类型和字段分别报告。Studio 直接使用结构化位置。完整检查和快速预览共用内容与依赖的诊断，包括缺锁和引用错误的位置。

在 `site/` 运行 `npm run check -- <游戏>` 或 `npm run check -- --package <包>`。包逐关独立检查，游戏另查编排和进度。省略目标时查全部游戏及未被游戏选用的包。空内容工作区也能执行。技术问题由检查报告，教学建议由评审处理。

流水线的 `domain` 闸门另外调用已登记的契约，检查派生结构、蓝图往返和作品行为。契约向闸门返回可定位的诊断。封装作品的检查由玩法执行，按发布任务分别用该任务的用例运行对应的元件版本。

### 5.1 关卡开发规范

以下规范供人和 agent 在设计、试玩和评审时遵守，不是自动审计规则，也不需要教学元数据。

- **按真实问题引入能力。** 一次围绕一个主要新想法组织任务，比较元件、设置或阶段带来的认知负担；几个元件是否属于同一个想法由作者结合问题判断，不声明概念标签。旧 `many-new` 的关切在这里评审，不机械计算元件数。
- **引入后尽快使用。** 新能力应在引入它的任务里发挥作用，并在后续任务或封装元件里继续使用。若它要等几个无关的新能力之后才用到，重新考虑引入位置；不为满足次数或间隔而补关。这取代 `idle-idea`。
- **首次体验能观察到意义。** 不把一句说明就能理解的工具拆成只放单个元件直连目标的关。假设框、区域、回溯等用法本身抽象时，可以安排专门体验，但应通过中间状态、对比或失败让玩家看见机制。通过实际任务和试玩判断是否达到这个效果。
- **形成可复用的抽象。** 检查搭出的作品是否在后续任务中复用；若参考解反复照抄已可封装的结构，判断是否应改用封装元件或调整课程位置。终局作品可以有独立价值，不必为每个作品安排后继关。这取代 `unused`、`bypass`。
- **控制当前任务的操作负担。** 看分段之后仍需操作多少个元件、手机是否能理解和完成；必要时拆任务、形成中间作品或减少无关元件。八个松散元件可以作为评审提示，不是 `open-crowded` 硬上限。
- **明确能力的来源。** 通常通过构建获得可复用作品，已有条件或借用工具可以由任务给出；不要为避免旧 `granted` 规则强迫玩家重造它。依赖已能携带的元件通常不用重复列在 `adds`，但重复声明不是 `carried` 技术错误。
- **按试玩证据判断难度。** 比较相邻任务的尝试、提示、放弃和用时，结合样本量与玩家背景诊断突增；不由固定比例或次数阈值自动判定 `difficulty-spike`。

玩家看到的「新」按这条先修路线中元件或阶段的首次引入计算，后续任务不重复标记；并行分支各按自己的先修计算。它不是认知负担的评分，也不按想法合并。新阶段显示在原元件卡片上。

### 5.2 规范提示

规范提示（`engine/advisories.js`）是机器看得出的行文惯例，例如各类文案的长度、口语和预告后文的措辞。它不是检查：不判定内容对错，不阻断写入、发布和部署，也不出现在 `check`、流水线、CLI 与 MCP 的任何输出里。人立的规则不一定适用于每一处，是否修改由人在 Studio 里逐条决定（见 [6.7](engine-studio.md)）。

划分标准：违反后内容无法加载、运行或通过参考解的，属于检查；违反时可能存在合理例外的，属于规范提示。规则与阈值只写在代码里，本手册和面向 agent 的写作规范不列举，以免为消除提示而牺牲内容质量。反复出现的问题由评审写成定性的意见交回作者。
