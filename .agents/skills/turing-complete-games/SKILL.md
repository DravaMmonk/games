# 类图灵完备学习游戏

## 当前内容

- 按用户给定的目标工作。用户委托设计时，结合课程资料、已有知识和实际玩法作出选择。
- 先用 MCP `inspect` 或在 `site/` 运行 `npm run --silent inspect -- <游戏> [chapter=<章节全名> | level=<关卡全名或地图编号>]`。查包职责与字段时读包声明、公开入口和 MCP `vocabulary`。选写操作前读 `npm run op -- list`。
- 通过 Studio、CLI 或 MCP 变更集编辑内容。对照 [共用架构](../../../games/design/engine.md) 核对层职责与依赖。[作者流程](../../../games/design/author-workflow.md) 给出读写与验证入口。

## 课程与玩法

- 从玩家可实际解决的问题、已有知识和可观察结果引入能力。先让玩家看见中间状态、对照或失败，再独立应用。需要时拆任务，避免无关的操作负担。
- 元件、配置和阶段在用到时提供。可复用产出在后续实际问题中使用。按真实先修关系安排路线。
- 用 [学习体验核对](references/learning-review.md) 辅助教学评审，按 [影响范围](../../../games/design/author-workflow.md#70-按影响范围验证) 验证。界面或交互变更需要桌面和手机实际流程。

## 游戏文案

按目标玩家的已有知识选择起点。关卡可复用实际先修任务已经教过的概念。新增游戏时，根据入门关卡补上主要受众、可假定的知识和教学起点。

| 游戏 | 主要受众 | 起点与知识边界 |
| --- | --- | --- |
| 视觉完备（`vision-complete`） | 第一次接触图像处理和计算机视觉的学习者 | 从照片、明暗、颜色和在网格上挪一格开始。像素的数值表示、卷积和频率等概念随关卡引入。 |
| 状态之图（`state-graph`） | 第一次接触算法、想通过解谜学习动态规划的玩家 | 可假定会数数、做简单加法和沿格子找路。从数路线和填表开始，逐步引入状态与递推。编程和算法知识从零起步。 |
| 证明完毕（`qed`） | 第一次接触形式逻辑和机器验算证明的学习者 | 从日常语句的真假和列举情况开始，逐步引入真值表、逻辑符号、证明规则和证明器。形式逻辑与证明助手知识从零起步。 |

用 ELI5（Explain Like I’m Five）解释新概念。从受众熟悉的事物和游戏里可观察、可操作的例子讲起，先说清动作与结果，再在需要时给出正式术语或符号。语气自然，保留条件、因果和适用范围。

说明类文字用标准术语，保持清爽简练。同一概念沿用游戏和词条里的规范名称。术语首次出现时，可用一句白话或一个具体例子解释；后文统一称呼，删去重复释义和铺垫。

### 按场景写作

- **引言**用通俗的短句承上启下。从玩家实际先修中学过的办法或看过的现象切入，用一个新情境或变化提出本关要解决的问题。入门关从日常经验切入。有配图时，指出图里值得观察的变化，把推理留给接下来的任务。
- **标题**用简短的词组点出这一关或任务的主要动作、现象或概念。优先用贴切的日常说法，沿用玩家已认识的名称，把操作细节留在简报或提示里。
- **任务简报**让玩家扫一眼就知道要做什么。用明确的动词写出操作，交代对象、必要条件和可判断的成功标准。只补充开始操作所需的情境或控件说明，用界面里的实际名称。
- **提示**先指出可以观察、对比或试验的线索，必要时再给出一个中间步骤。多条提示按玩家卡住的程度逐步展开。
- **结语**从玩家刚看到的结果提炼核心思路，解释它为什么成立、在什么条件下适用，并用具体例子把直觉接到相关的专业术语或学科知识上。解释应适用于不同的正确解法。有自然的延伸时，留一个可以继续推想的问题，例如「如果路能绕回原处，还能按原来的顺序填表吗？」
- **界面文案**保持清爽。按钮用简短动词标出动作，标签直接命名对象或状态，反馈说清结果、具体问题和可行的下一步。删去界面已清楚表达的信息和重复说明。

分别读一遍中英文。核对术语、条件和操作是否一致，确认玩家凭当前关卡和实际先修内容就能开始操作、理解结果，并检查受影响的标题、简报和控件在桌面与手机上都易于扫读。

稳定的共用架构约定集中在 [项目手册](../../../games/design/README.md)。包声明、实际内容和代码直接供作者工具读取。
